# 崩溃修复记录 · v2.0 → v2.1

## 一、这次崩在哪

崩溃报告：`crash-2026-10-22_15.55.54-fml.txt`
错误类型：`ModLoadingCrashException — Mod loading has failed`

**根因：v2.0 只验证了"每个模组本身有 1.21.1/NeoForge 版本"，没有验证"它们的前置依赖也在包里"。**

NeoForge 遇到任何一个 `required` 依赖缺失，整个游戏在 mod 扫描阶段就停止，一个模组都不加载。

v2.0 一共 203 个模组，其中 **37 个 modId 的依赖没人满足**。

## 二、怎么查出来的

不是靠猜。直接读你已经下载好的 `mods/` 目录：

1. 逐个打开 jar，读里面的 `META-INF/neoforge.mods.toml`
2. 解析 `[[dependencies.<modid>]]` 段，取出 `modId` + `type=required`
3. 与"已装的 modId 集合"对比 → 得到缺失表
4. 再读每个 jar 的 `META-INF/jarjar/metadata.json`，排除掉**已经内嵌**的那些

第 4 步很关键，否则会误报。例如：

| 被误报为"缺失" | 实际情况 |
|---|---|
| `flywheel` | Create 6.0.10 的 jarjar 里已经带了 `flywheel-neoforge-1.21.1` |
| `ponder` | 同上，Create 内置 |
| `apollib` | `lithostitched` 内置 |
| `mezz_config` | `jei` 内置 |
| `greenhouseconfig` | `BrewinAndChewin` 内置 |
| `extensibleenums` | `IllagerInvasion` 内置 |
| `endercore` | `enderio` 内置 |
| `flightlib` | `create_jetpack` 内置 |
| `xaerolib` | `xaerominimap` / `xaeroworldmap` 内置 |
| `kotlinforforge` | 已装（5.12.0），FML 日志里能看到已加载 |

排除这些之后，**真正缺失 27 个**。

## 五、1 个打包错误（已就地修复）

`Structory_Towers_26.2_v1.0.17.jar`：

```
Failure message: File mods\Structory_Towers_26.2_v1.0.17.jar is not a valid mod file
Exception message: Missing ModLoader in file
```

作者（Stardust Labs）在这个 jar 里放了两个 toml：
- `META-INF/neoforge.mods.toml` ← **缺 `modLoader` 字段**
- `META-INF/mods.toml` ← 有 `modLoader="lowcodefml"`

FML 优先读 `neoforge.mods.toml`，读到没有 `modLoader` 就直接崩。

**修复方式：删掉 `META-INF/neoforge.mods.toml`，让它回退到 `mods.toml`。**
修复脚本会就地重写这个 jar，不用重新下载。

## 七、如果还崩

按这个顺序看：

1. **先看崩溃报告第一段** `Failure message`，它直接写缺什么
2. 如果是 `requires xxx x.y.z or above / Currently, xxx is not installed`
   → 还有个前置没补。把 modId 发我，或者自己去 Modrinth 搜这个 modId
3. 如果是 `is incompatible with`
   → 两个模组互斥，删一个
4. 如果是 `Missing ModLoader` / `not a valid mod file`
   → 那个 jar 打包有问题，看它有没有 `META-INF/mods.toml`，有就把 `neoforge.mods.toml` 删掉
5. 如果卡在 `KubeJS loading scripts`
   → 看 `logs/kubejs/server.txt`

## 八、为什么 v2.0 会漏

因为我用的是"逐个模组查可用版本"，而不是"解析依赖图"。

Modrinth API 的 `/v2/version/{id}` 里有 `dependencies` 数组，带 `project_id` 和 `dependency_type`。
正确的做法是：拿这个数组做 BFS 闭包，缺什么补什么。

v2.1 已经这么做了，并且额外用"读真实 jar 的 mods.toml"做了交叉验证——
因为 Modrinth 上的依赖元数据有时候不写全（反过来，jar 里可能有 API 没标的内嵌依赖）。

# 第二轮崩溃（2026-10-28 17:38）

## 现象

`latest.log` 里只有三行有用信息：

```
[main/ERROR]: Missing or unsupported mandatory dependencies:
[Render thread/FATAL]: Mod untamedwilds requires citadel 2.7.5
[Render thread/FATAL]: Mod reeses_sodium_options is incompatible with sodiumoptionsapi 0 or above
```

其余满屏 `Cowardly refusing to send event ... to a broken mod state` 都是**结果**不是原因——
mod 状态一旦 broken，NeoForge 就拒绝派发所有渲染事件。

## 两个根因

### 1. `sodiumoptionsapi` 没被删掉

`fix_mods.ps1` 里我写的匹配键是 `"sodium-options-api"`（带连字符），
但实际文件名是 `sodiumoptionsapi-neoforge-1.0.10-1.21.1.jar`（**没有连字符**）。

`-like "*sodium-options-api*"` 匹配失败 → 文件留着 → 和 `reeses-sodium-options` 冲突。

**已修**：匹配键加了一条 `sodiumoptionsapi`（7 条规则）。

### 2. `untamedwilds` 锁死了 citadel 精确版本

它的 `mods.toml`：

```toml
[[dependencies.untamedwilds]]
    modId="citadel"
    versionRange="[2.7.5]"
```

`[2.7.5]` 是**精确版本**，不是范围。当前装的 `citadel-1.21.1-2.7.6` 不满足。

Modrinth 上 `citadel-1.21.1-port` 确实有 2.7.5，但要下载。

**不下载的解法**：把 `[2.7.5]` 改成 `[2.7.5,)`，直接重打包 jar。

## 处理结果

| 项 | 处理 |
|---|---|
| `sodiumoptionsapi-neoforge-1.0.10-1.21.1.jar` | 移到 `_disabled_mods/` |
| `untamedwilds-1.21.1-3.0.1.jar` | 重打包成 `...-patched.jar`，版本锁放宽 |
| `_godpath_removed/`（在 mods 里） | 移到版本根目录 `_disabled_mods/`，避免被扫描器看到 |

**禁用目录放在 `mods/` 外面**，因为不确定某些版本会不会递归扫描子目录。

## 最终校验

用 `tomllib`（Python 标准库，不是正则）重新解析全部 242 个 jar 的 `mods.toml`：

```
jar 总数      : 242
已安装 modId  : 244
真正缺失的前置 (0): （无）
```

唯一解析不了的是 `kotlinforforge-5.12.0-all.jar`——它是 fat jar，`mods.toml` 不在标准路径，
但 FML 日志里能看到 `kotlinforforge@5.12.0` 已作为 language provider 加载，正常。

## 为什么前两次扫描会误报

`mods.toml` 里 `modId` 出现**两次以上**：
一次在 `[[mods]]` 段（本 mod 自己），一次在 `[[dependencies.X]]` 段（依赖名）。

而且**顺序不固定**——`configurable` 的 toml 里 `[[dependencies]]` 写在 `[[mods]]` 前面，
`fragmentum` 的 `[[mods]]` 里第一个 modId 是 `minecraft`。

用正则取"第一个 modId"会把它们判错。正确做法是用 TOML 解析器按语义取值。

# 第三轮崩溃（2026-10-28 21:28）· JPMS 模块冲突

## 现象

这次没有依赖缺失，也没有 mod 报 requires。整份日志只有一条：

```
java.lang.module.ResolutionException:
Modules forgeconfigapiport and untamedwilds export package
net.minecraftforge.fml.config to module naturalist
```

崩在 `ModuleLayerHandler.buildLayer()` —— **比依赖检查更早的阶段**，连 mod 主类都没加载到。

## 根因

Java 的模块系统（JPMS）不允许两个模块向同一个模块导出同一个包。

`untamedwilds` 这个 jar 里**自带**了 Forge Config API 的类：

```
net/minecraftforge/fml/config/ModConfig.class
net/minecraftforge/fml/config/ModConfig$Type.class
```

而 `ForgeConfigAPIPort` 本来就应该提供这个包。两者同时向 `naturalist` 导出 → 直接拒绝。

`untamedwilds` 是从 Forge 移植过来的，作者把 Forge Config API 的类直接打进了自己的 jar，这是移植版的通病。

## 为什么之前没暴露

上一轮它因为 `requires citadel 2.7.5` 崩在**更早**的依赖检查阶段，
根本没走到模块解析，所以这个冲突一直藏着。

我上一轮把它的版本锁 `[2.7.5]` 改成了 `[2.7.5,)`（重打包 jar），
它这才通过依赖检查，走进模块解析，把第二个问题暴露出来。

**教训**：这种移植版应该直接删，不该做版本锁补丁。

## 验证：我的补丁没有破坏 jar

对比原版和修补版：

```
原版  : 2053 条目 · 无 module-info · 3 个 net/minecraftforge/fml/config 类
修补版: 2053 条目 · 无 module-info · 3 个 net/minecraftforge/fml/config 类
```

结构完全一致。那个包本来就在里面，不是我加的。

## 处理

| 文件 | 处理 |
|---|---|
| `untamedwilds-1.21.1-3.0.1.jar`（原版） | 移到 `_disabled_mods/` |
| `untamedwilds-1.21.1-3.0.1-patched.jar` | 移到 `_disabled_mods/` |

两个都清掉，因为模块冲突与版本无关。

## 最终校验

**1. 共享包重复扫描**（`net/minecraftforge/**` + `net/neoforged/**`）

```
被 >=2 个 jar 同时包含的包：0
```

**2. 依赖闭包扫描**（tomllib 解析 241 个 jar）

```
jar 总数      : 241
已安装 modId  : 243
真正缺失的前置 : 0
```

两项都干净。

## 三次崩溃的规律

| 轮次 | 阶段 | 原因 | 教训 |
|---|---|---|---|
| 第一次 | mod 扫描 | 27 个前置没装 | 要解析依赖图，不能只看 mod 本体 |
| 第二次 | 依赖检查 | sodiumoptionsapi 文件名匹配漏 + citadel 版本锁 | 正则匹配要覆盖文件名变体 |
| 第三次 | **模块解析** | untamedwilds 自带 fml/config 包 | 移植版别打补丁，直接删 |

每一次都修好了上一层，才露出下一层。这类整合包的启动链是分阶段失败的，
必须一层层过。
